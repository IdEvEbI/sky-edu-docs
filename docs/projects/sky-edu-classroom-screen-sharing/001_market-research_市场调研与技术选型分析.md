## 1. 市场调研

### 1.1 现有产品分析

#### 1.1.1 在线教育平台类

**雨课堂**

- **优势**：与清华大学合作，教育场景专业；支持课堂互动、作业布置
- **劣势**：依赖互联网，局域网环境性能差；功能复杂，学习成本高
- **适用性**：❌ 不适合局域网环境

**腾讯课堂**

- **优势**：用户基数大，功能完善；支持直播、录播、互动
- **劣势**：网络依赖强，延迟较高；商业化程度高，成本高
- **适用性**：❌ 不适合局域网环境

**钉钉课堂**

- **优势**：企业级应用，稳定性好；集成度高
- **劣势**：功能冗余，界面复杂；局域网优化不足
- **适用性**：❌ 不适合局域网环境

#### 1.1.2 屏幕共享工具类

**TeamViewer**

- **优势**：跨平台支持好，安全性高；功能丰富
- **劣势**：商业软件，成本高；局域网优化不足；功能冗余
- **适用性**：⚠️ 部分适用，但成本高

**AnyDesk**

- **优势**：低延迟，性能好；跨平台支持
- **劣势**：商业软件；缺乏教育场景定制
- **适用性**：⚠️ 技术参考价值高

**VNC Connect**

- **优势**：开源方案，可定制；跨平台支持
- **劣势**：延迟较高；缺乏现代 UI；功能单一
- **适用性**：⚠️ 技术参考价值

#### 1.1.3 专业教学软件类

**联想传奇因特网电子教室**

- **优势**：专为教育设计，功能完整；集成度高
- **劣势**：硬件依赖强，成本高；系统复杂；更新缓慢
- **适用性**：⚠️ 功能参考价值

**必捷多媒体协作系统**

- **优势**：支持多种投屏协议；BYOD 模式
- **劣势**：需要额外硬件；网络要求高；成本较高
- **适用性**：⚠️ 部分功能参考

**EV屏幕共享**

- **优势**：专注局域网场景，延迟低至100ms；跨平台支持；功能完整；教育场景定制
- **劣势**：商业软件，成本高；最多50台设备，无法满足200人需求；功能冗余
- **适用性**：⚠️ 直接竞品，需要差异化竞争

### 1.2 市场空白分析

#### 1.2.1 现有产品痛点

**网络环境痛点**：

- 现有产品主要针对互联网环境设计
- 局域网环境下的延迟和带宽优化不足
- 缺乏针对教育场景的局域网优化

**功能痛点**：

- 功能冗余，缺乏教育场景定制
- 界面复杂，教师学习成本高
- 缺乏教学数据采集和分析

**成本痛点**：

- 商业软件成本高，不适合预算有限的学校
- 硬件依赖强，部署成本高
- 缺乏开源或低成本解决方案

**竞争痛点**：

- EV屏幕共享等产品已占据市场，但并发规模有限（最多50台）
- 现有产品功能冗余，缺乏深度定制
- 无法与现有教学业务系统深度集成

#### 1.2.2 市场机会

**技术机会**：

- WebRTC 技术成熟，可实现低延迟屏幕共享
- Electron 等跨平台框架降低开发成本
- 局域网环境下的性能优化空间大

**市场机会**：

- 专注局域网场景的产品较少
- 教育场景定制化需求未被满足
- 开源教育软件市场空间大
- EV屏幕共享等产品并发规模有限，存在技术突破空间
- 现有产品无法与教学业务系统深度集成

## 2. 技术选型分析

### 2.1 技术栈对比

#### 2.1.1 桌面应用框架

**Electron + React**

- **优势**：开发效率高，跨平台支持好；Web 技术栈，开发成本低；生态丰富
- **劣势**：内存占用较高；性能不如原生应用
- **适用性**：✅ 推荐，适合快速开发和迭代

**Qt + C++**

- **优势**：性能高，内存占用低；跨平台支持好
- **劣势**：开发周期长；学习成本高；UI 开发复杂
- **适用性**：⚠️ 适合性能要求极高的场景

**.NET + C#**

- **优势**：Windows 平台兼容性好；开发效率高
- **劣势**：跨平台支持有限；Mac 支持较差
- **适用性**：⚠️ 适合纯 Windows 环境

#### 2.1.2 网络通信协议

**WebRTC**

- **优势**：专为实时通信设计；浏览器原生支持；延迟低
- **劣势**：实现复杂度较高；调试困难
- **适用性**：✅ 推荐，适合屏幕共享场景

**WebSocket**

- **优势**：实现简单；全双工通信；浏览器支持好
- **劣势**：需要应用层协议；延迟相对较高
- **适用性**：✅ 推荐，适合信令和控制消息

**UDP + 自定义协议**

- **优势**：延迟最低；带宽利用率高；可控性强
- **劣势**：实现复杂；需要处理丢包和重传
- **适用性**：⚠️ 适合对延迟要求极高的场景

#### 2.1.3 音视频处理

**H.264 编码**

- **优势**：压缩率高；硬件支持好；兼容性强
- **劣势**：专利费用；编码复杂度高
- **适用性**：✅ 推荐，适合高质量视频传输

**VP8/VP9 编码**

- **优势**：开源免费；WebRTC 原生支持
- **劣势**：硬件支持有限；压缩率不如 H.264
- **适用性**：⚠️ 适合开源项目

**FFmpeg**

- **优势**：功能强大；支持多种格式；社区活跃
- **劣势**：体积较大；学习成本高
- **适用性**：✅ 推荐，适合音视频处理

### 2.2 推荐技术栈

#### 2.2.1 核心技术栈

**桌面应用**：

- **框架**：Electron + React + TypeScript
- **理由**：开发效率高，跨平台支持好，适合快速迭代

**网络通信**：

- **屏幕共享**：WebRTC Screen Capture API
- **信令服务**：WebSocket + Node.js
- **理由**：WebRTC 专为实时通信设计，延迟低

**音视频处理**：

- **编码**：H.264（硬件加速）
- **处理**：FFmpeg + WebRTC
- **理由**：H.264 压缩率高，FFmpeg 功能强大

**数据存储**：

- **本地数据库**：SQLite
- **文件存储**：本地文件系统
- **理由**：轻量级，适合局域网环境

#### 2.2.2 开发环境

**开发工具**：

- **IDE**：VS Code + 相关插件
- **版本控制**：Git + GitHub
- **包管理**：npm / yarn

**测试框架**：

- **单元测试**：Jest + React Testing Library
- **集成测试**：Cypress
- **理由**：TDD 开发模式，保证代码质量

**构建部署**：

- **构建工具**：Webpack + Electron Builder
- **CI/CD**：GitHub Actions
- **理由**：自动化构建和部署

### 2.3 技术选型理由

#### 2.3.1 选择 Electron 的理由

**开发效率**：

- Web 技术栈，开发成本低
- 丰富的 UI 组件库（Ant Design）
- 热重载，开发体验好

**跨平台支持**：

- 一套代码，多平台运行
- Windows / macOS / Linux 支持
- 后续移动端扩展容易

**生态丰富**：

- npm 包生态完善
- 社区活跃，问题解决容易
- 第三方库支持好

#### 2.3.2 选择 WebRTC 的理由

**实时性**：

- 专为实时通信设计
- 延迟低（< 100ms）
- 适合屏幕共享场景

**标准化**：

- W3C 标准，浏览器原生支持
- 无需额外插件
- 未来兼容性好

**功能完整**：

- 屏幕捕获、音视频传输一体化
- 支持多种编码格式
- 网络自适应

#### 2.3.3 选择 SQLite 的理由

**轻量级**：

- 无需额外数据库服务器
- 部署简单，维护成本低
- 适合局域网环境

**性能好**：

- 读写性能高
- 支持并发访问
- 数据完整性好

**跨平台**：

- 多平台支持
- 无需额外配置
- 数据迁移容易

## 3. 技术风险评估

### 3.1 主要风险

**性能风险**：

- Electron 内存占用较高
- 200 人并发可能影响性能
- **缓解措施**：性能优化，分批处理

**兼容性风险**：

- WebRTC 在不同浏览器表现差异
- 硬件编码支持差异
- **缓解措施**：兼容性测试，降级方案

**网络风险**：

- 局域网环境复杂
- 交换机配置影响性能
- **缓解措施**：网络优化，自适应码率

### 3.2 风险缓解策略

**技术风险**：

- 原型验证，提前发现技术问题
- 性能测试，确保满足需求
- 兼容性测试，覆盖主流环境

**项目风险**：

- 敏捷开发，快速迭代
- TDD 开发，保证代码质量
- 用户反馈，及时调整方向

- EV屏幕共享等产品并发规模有限（最多50台），存在技术突破空间

- 开发效率高，跨平台支持好
